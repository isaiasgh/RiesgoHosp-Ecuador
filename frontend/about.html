Acerca del proyecto

Esta interfaz representa un sistema experimental diseñado para estimar la probabilidad de mortalidad intrahospitalaria de un paciente. Las inferencias se realizan evaluando exclusivamente la información temprana disponible al momento del ingreso al establecimiento de salud, tal como factores demográficos, ubicación, tipo de establecimiento y modalidad de aseguramiento.

El modelo fue entrenado utilizando el registro histórico de Egresos Hospitalarios del Ecuador (INEC). El propósito de la herramienta es servir como un recurso predictivo de apoyo al triaje y priorización de pacientes, contribuyendo a la optimización de los recursos médicos desde el minuto cero.

Nota: Este resultado es una estimación estadística basada en patrones de datos históricos generada por algoritmos de Machine Learning. En ningún caso constituye un diagnóstico clínico o sustituye la valoración de un profesional médico certificado.

Guía de Uso

  1. Navegue hacia la pestaña Predictor en el menú superior.
  2. Para una demostración rápida, utilice el botón «Cargar datos de prueba». Esto inyectará un caso simulado válido dentro de todos los campos requeridos del formulario.
  3. Para realizar pruebas masivas, utilice el botón «Cargar archivo JSON» para subir un lote de datos estructurados:
    • Si el archivo contiene un objeto individual ({ ... }), los datos poblarán el formulario de forma inmediata.
    • Si el archivo contiene un arreglo de múltiples pacientes ([{ ... }, { ... }]), se habilitará una tabla de previsualización. Puede interactuar con cualquier fila para poblar el formulario con ese registro específico, o utilizar el botón «Seleccionar paciente al azar».
  4. Haga clic en «Predecir riesgo». El panel lateral cambiará su estado a «Procesando...» mientras el modelo remoto procesa el vector de características.
  5. Tras una ejecución exitosa, la interfaz presentará la probabilidad de mortalidad del paciente. Si la estimación supera el umbral matemático definido, se activará una bandera de Riesgo alto.
  6. Si los datos enviados no cumplen con los esquemas de validación del sistema, el servidor rechazará la solicitud (HTTP 422 Unprocessable Entity) y se detallarán los campos con errores en rojo.

Arquitectura Técnica

La solución está implementada bajo una arquitectura Cliente-Servidor desacoplada. El cliente es una interfaz estática ligera que se comunica mediante solicitudes HTTP asíncronas con una API RESTful que aloja los artefactos binarios del modelo predictivo.

Componente Tecnologías Descripción
Cliente Web (Frontend) Vanilla HTML5, CSS3, JS Nativo Garantiza una interfaz ultraligera, libre de dependencias o compiladores. Gestiona la captura de los inputs, orquesta la carga de archivos locales vía FileReader API y realiza las peticiones fetch() a la API.
Capa de Servicios (Backend) FastAPI, Uvicorn, Pydantic Expone el servicio de inferencia en /api/v1/predict/riesgo-mortalidad. Garantiza validaciones de tipos estrictas y gestiona la carga en memoria de los artefactos predictivos.
Ingeniería de Características Scikit-learn, Imbalanced-learn Aplica un Pipeline encapsulado. Normaliza unidades de medida heterogéneas (ej. edad en horas vs años), aplica imputación estadística a variables faltantes, balancea las clases mediante SMOTE y codifica la matriz de datos con OneHotEncoder.

Nota Crítica: Se descartaron por completo las variables de diagnóstico definitivo (Causas CIE-10) del dataset original para evitar fenómenos de Data Leakage (fuga de información), garantizando que el modelo opere únicamente con datos reales de ingreso.
Modelado Inicial Perceptrón Simple, MLP, CNN 1D y LSTM Durante la experimentación, se ajustaron y evaluaron múltiples arquitecturas bajo optimización de hiperparámetros automatizada para encontrar la mejor aproximación al problema.
Modelo en Producción Regresión Logística El algoritmo de Regresión Logística fue seleccionado como el modelo final en producción debido a que maximizó la métrica Recall de la clase minoritaria, priorizando la sensibilidad clínica para asegurar la detección de la mayor cantidad de pacientes en verdadero riesgo, superando la complejidad de las redes neuronales en este escenario tabular específico.

Formato de Comunicación

El frontend envía un POST con el cuerpo en formato JSON hacia la API, compuesto por un vector estricto de 20 campos por paciente, correspondientes a: ubicación y tipo del establecimiento, datos demográficos, aseguramiento del paciente, residencia, y fecha de ingreso.

La respuesta exitosa incluye tres campos: la probabilidad calculada (proba), la bandera booleana de riesgo alto (riesgo_alto, verdadera si proba supera el umbral de decisión configurado en el servidor) y el nombre del algoritmo usado (modelo_usado). Si algún campo no cumple el esquema establecido, la API responde con código 422 y el listado de errores de validación estructurados.

Interfaz de demostración — consume la API local en http://127.0.0.1:8000/api/v1/predict/riesgo-mortalidad.
